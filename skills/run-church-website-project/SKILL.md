# Run a Church Website Project

Guide the project through conversations, evidence, canonical DNA documents, visitor strategy, copy, design, build, and launch without inventing church facts.

## Find the project

If no private project workspace exists, read [start-and-route.md](references/start-and-route.md) and begin with its guided setup conversation. Do not require the participant to prefill a questionnaire, template, or prompt. Ask for the minimum setup information conversationally, write the answers into the project files, and accept `unknown` without blocking progress. Once the church name and workspace location are known, locate the Church Website Blueprint repository and run its project initializer. Do not place church-specific data in the public toolkit repository.

If a project exists, read these files before acting:

- `workflow-lock.yml`
- `00-admin/project-state.md`
- `00-admin/coverage-matrix.md`
- `00-admin/open-questions.md`
- `00-admin/decision-log.md`
- `00-admin/approvals.md`

Use the project's pinned toolkit version. Do not silently migrate it.

## Preserve the central boundary

AI may organize, clarify, condense, compare, and propose. It may not invent church facts, doctrine, programs, policies, promises, stories, biographies, or operational details.

- Separate current truth from aspiration.
- Record contradictions; do not resolve them through prose.
- Mark privacy restrictions.
- Preserve source attribution for consequential claims.
- Turn missing evidence into a question.
- Keep research-based recommendations labeled and separate from church-source truth.

## Route by current need

### Initialize or determine project path

Read [start-and-route.md](references/start-and-route.md). Use it for new projects, redesigns, targeted improvements, unclear scope, and zero-preparation launch conversations. The agent conducts the setup and records the answers; the human is not assigned form-filling homework.

### Assess an existing site

Read [existing-site.md](references/existing-site.md). Use it to inventory current evidence and test whether visitors can understand the church, determine fit, and take a next step.

### Prepare, conduct, or process discovery

Read [discovery.md](references/discovery.md). Use it for Conversation Briefs, interviews, transcripts, fact extraction, coverage updates, and follow-up routing.

### Build DNA, strategy, copy, or design artifacts

Read [content-and-design.md](references/content-and-design.md). Use it after sufficient discovery evidence exists.

### Review, launch, or maintain

Read [review-and-launch.md](references/review-and-launch.md). Use it for milestone approvals, staging validation, ownership, launch, and ongoing maintenance.

## Update state every time

After a substantive turn:

1. save new source material in `01-sources/`;
2. update the relevant ledger, DNA, strategy, copy, design, or QA artifact;
3. update the coverage matrix;
4. add or resolve open questions and decisions;
5. record approvals only when an authorized person has approved a defined scope;
6. update project state with one concrete next action and owner.

Do not declare the project complete merely because the current conversation ended.

## Keep the human interface small

Default participant-facing assets:

1. Project Launch Sheet
2. Existing-Site Findings Brief, when applicable
3. Conversation Brief
4. What We Heard + Open Questions
5. Milestone Review Packet
6. Launch and Ownership Sheet

Do not expose participants to the entire internal file tree when a focused review asset will do.

## Completion standard

The process is complete when approved DNA supports the public copy, visitors can understand identity and fit, critical journeys work, factual and privacy checks pass, ongoing owners are assigned, and launch approval is recorded.
